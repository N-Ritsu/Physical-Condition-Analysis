# Physical-Condition-Analysis

就労移行支援向け 体調・睡眠分析ダッシュボード。日報Excelから入眠時間・起床時間・睡眠時間・睡眠の質・中途覚醒回数・気分を抽出してグラフ化し、統計値と条件分岐による即時の振り返りコメントを表示するStreamlitアプリ。

設計の背景は [docs](docs/) 内のヒアリング議事録・課題定義書・要件定義書・ワイヤーフレームを参照。

## セットアップ

```bash
pip install -r requirements.txt
```

テスト・Lintも行う開発時は、`requirements-dev.txt`（pytest・ruffを追加）を使う。

## データ配置

`data/` 直下に利用者ごとのフォルダを作り、その中にExcelを置く（例: `data/西村/`）。サイドバーの「利用者」で表示する人を選ぶ。ファイル名は自由だが、名前に以下の文字列を含むxlsxを自動で見分ける（該当が複数ある場合は更新日時が最も新しいもの）。

- 名前に「日報」を含むxlsx: 日報Excel（列: 日付・就寝時間・起床時間・睡眠の質・気分（起床時）・気分（通所時）等）。見つからない場合、アプリ上にアップロード画面が表示される。
- 名前に「欠席」を含むxlsx: 欠席フォームの回答（「タイムスタンプ」列の日付を欠席日として使う）。「出席状況」の表示でのみ使い、無い場合は出席率を計算できない旨を表示する。
- 名前に「セルフケア」を含むxlsx: 月ごとにシートが分かれたセルフケアチェック表（〇/△/✕）。グラフのマーカー（○/△/×＝体調）はこのファイルから計算する。見つからない場合、マーカーはすべて「記録なし（早退等の可能性）」として黒い□で表示される。

個人の健康データのため `data/**/*.xlsx` は `.gitignore` 済み。支援員向けの入れ替え手順は [staff_operation_guide.md](staff_operation_guide.md) を参照。

### アプリの画面からの取り込み（データ管理）

エクスプローラーでフォルダを作らなくても、画面から利用者の追加と、日報・セルフケアシート・欠席情報（Excel）のアップロードができる（[data_management.py](src/health_dashboard/data_management.py)）。利用者の追加は、サイドバーの「利用者」のプルダウンの最後にある「新しい利用者を追加」を選んで行う（利用者が1人もいないときは、これが最初から選ばれ、追加の画面が開く）。アップロードは、サイドバーの「設定」の「データ管理」から行う（「設定」は「表示」とは別のグループで、どちらか一方だけが選ばれた状態になる）（選択中の利用者に日報がないときは、この画面が自動で開く）。

- 利用者の追加: 名前を入力して追加すると、data/ の下に同名のフォルダを作り、その利用者を選択する。使えない文字（\ / : * ? " < > |）、先頭・末尾の「.」、40文字超、Windowsの予約名、すでにいる利用者との重複（大文字小文字を区別しない）は断る。
- アップロード: ファイルを一時ファイルに保存し、その種類として読めることを確かめてから、同じ種類の古いファイル（名前に「日報」「セルフケア」「欠席」を含むもの）を全て削除して、「日報.xlsx」「セルフケアシート.xlsx」「欠席.xlsx」として保存する。別の種類のファイルや壊れたファイルは断り、今あるデータには触れない。Excelで開いたままで置き換えられないときは、その旨を表示する。
- 取り込んだ直後も画面は「データ管理」にとどまる（続けて次のファイルを入れられる）。

## データ解釈に関する注意（実データの制約に基づく調整）

- **入眠時間**: 元データには「就寝時間」列のみ存在し、9〜11時台の値はAM/PM区別なく記録されている（例: 実際は21:30就寝でも `09:30` と記録）。そのため6〜11時台の値はPM（+12時間）として正規化している（[data_loader.py](src/health_dashboard/data_loader.py) の `normalize_bedtime`）。
- **中途覚醒回数**: 独立した列がなく、「睡眠の質」列の自由記述（例: `悪い, 中途覚醒３以上`）から抽出している。「３以上」は3として扱い、「早朝覚醒」の記載は中途覚醒回数に+1として合算する。睡眠の質評価が複数併記されている行は、より悪い方（良好<普通<悪い）を採用する。
- **気分**: 「気分（起床時）」「気分（通所時）」の2系列があるため、縦軸の選択肢として両方を用意している。
- **体調マーカー（○/△/×）**: セルフケアシートの「睡眠・食事・ストレス」「良好サイン」「注意サイン」「悪化サイン」「回復対処」の全チェック項目（備考欄を除く）を、〇=0点・△=1点・✕=2点として日ごとに合算し、0点=○良好／1〜2点=△普通／3点=×注意／4点=×警戒／5点以上=×異常の5段階に変換している（[data_loader.py](src/health_dashboard/data_loader.py) の `CONDITION_CAUTION_POINTS` / `CONDITION_WARNING_POINTS` / `CONDITION_ABNORMAL_THRESHOLD`）。3〜5点の区切りは実データの分布（0点の日を除くと1〜4点に集中し、7点以上は明確な外れ値）に基づく初期値で、現場の実感に応じて調整可能。日報はあるがセルフケアシートに記録がない日は、早退等により記入できなかった可能性を示すサインとして黒い□で表示する。

## 振り返りコメントの生成方式（統計値と条件分岐、LLM不使用）

振り返りコメントは統計値を条件分岐だけで文章化する（[rule_based_insight.py](src/health_dashboard/rule_based_insight.py)）。待ち時間ゼロで、文面が事前に固定されているためガードレールも構造的に保証される。以下の分析を組み合わせている。

- 線形回帰によるトレンド検出。決定係数（R²）が低い（ばらつきが大きい）場合は「目安としてご覧ください」と留保を付ける。
- 軸ごとの「良し悪しの方向性」（`data_loader.py`の`AXIS_DIRECTION`）を踏まえたトレンドの評価。入眠時間・起床時間は安定度のみ、中途覚醒回数は少ないほど良い、睡眠の質・気分は多いほど良い、として増減を「良い方向」「注意したい方向」と言い分ける。
- 直近値のzスコアによる外れ値検知。
- 体調（セルフケアシート由来）が「注意」以上の状態が続いている場合のストリーク検知（選択中の軸に関わらず評価）。
- 期間内の安定度比較。「全期間」表示では4週間単位、「直近1ヶ月」表示では1週間単位でローリング集計し、最も安定していた期間・最も不安定だった期間を検出して直近の期間と比較する（差が小さければ「安定」とだけ言及。最も安定していたウィンドウ自体のばらつきが大きい場合は「常に不安定」と判定する）。
- 期間内の水準（良し悪し）比較。安定度比較と同じウィンドウを使い、軸の「良し悪しの方向性」を踏まえて最も値が良かった期間・悪かった期間を検出する。「最も安定していた期間」が必ずしも「値が最も良かった期間」とは限らないため（例: 中途覚醒回数が一定して2回だった期間より、ばらつきはあっても0回に近い期間の方が良い）、安定度比較とは別の文で言及する。方向性のない軸（入眠時間・起床時間）では評価しない。

- グラフの背景色。振り返りコメントが「最も安定」「ばらつきが最も大きい」「最も良い状態」と述べる期間を、グラフの背景で色づけする（薄い青＝最も安定していた期間、薄い赤＝ばらつきが最も大きかった期間、薄い緑＝最も良い状態だった期間）。期間が重なる部分は赤＞緑＞青の優先度で1色にする。コメントにその期間が書かれる場合にだけ色づけし、方向性のない軸（入眠時間・起床時間・睡眠時間）では緑は出ない。
- 個人ごとの悪化ボーダー（[border_analysis.py](src/health_dashboard/border_analysis.py)）。振り返りコメントの文章には含めず、コメントの上に「悪化ボーダー」として独立して表示する。グラフには、ボーダーの値に90%=赤・80%=黄・70%=青の破線を引く。その人の過去の記録（全期間）から、選択中の項目がどの値を超える（少ないほど悪い項目は下回る）と、体調が×（注意以上）になる割合が90%以上なら「極めて危険な報告」、80%以上なら「危険な報告」、70%以上なら「注意すべき報告」とする。各報告について、その割合を満たす中で最も手前の値をボーダーとし、同じボーダーが複数の報告を満たす場合は最も重い報告だけを出す。「（10日中9日）」のように該当日数を必ず併記する。直近の値がボーダーを超えていれば、パネルにその旨を示し、振り返りコメントの締めの一文も注意喚起にする。偶然による偏りを避けるため、ボーダーを超えた日が4日未満のもの、体調の記録が10日未満の場合、もともと×が多くて値による差が小さい場合（超えた日と超えていない日の×の割合の差が30ポイント未満）は出さない（border_analysis.py の定数で調整できる）。入眠時間・起床時間・睡眠時間は良し悪しの方向性がないため、高い側・低い側の両方を調べる。精神状態（選択式）は対象外で、気圧は対象に含む。気圧（前日差）は「0に近いほど良い」項目として、前日から上がった場合も下がった場合も合わせて、0からの離れ具合（「±3.0hPa以上動いた日」）でボーダーを調べ、グラフには0の上下に2本の線を引く。

締めの一文は、上記の分析結果に応じて3パターンに出し分ける（`_closing_phrase`）。

1. 直近に悪化傾向・悪化方向の外れ値・体調の注意ストリーク・不安定期や悪い水準の期間への接近のいずれかがあれば、支援員に気にかけてあげるよう促す。
2. 直近は問題ないが、期間内で安定/不安定、または良かった/悪かった時期の差が大きい場合は、それぞれの時期の生活リズムを比較する自己分析を促す。
3. どちらでもなければ、期間を通して安定しており大きな問題は見られない旨を伝える。

支援員が医療職ではないことを前提に、以下を厳守する。

- 医学的診断・病名判断・服薬に関する言及をしない。
- 断定的な因果関係を主張しない。
- 「〜の傾向が見られます」という対話補助のトーンに限定する。
- 利用者の日報・セルフケアのデータは外部送信しない（気象データの取得時に送る情報は「気象データ」の節を参照）。

なお、当初はローカルLLM（Ollama + qwen3:8b）による考察生成もあわせて実装していたが、GPUのない環境での生成時間の長さ・AI出力自体への支援員の不安感・条件分岐のみでの分析精度が実用上十分だったことから、条件分岐のみの方式に一本化した。経緯は [docs/05_prototype_creation_progress.md](docs/05_prototype_creation_progress.md) を参照。

## 相関表

サイドバーの「表示」で「相関表」を選ぶと、7つの指標（入眠時間・起床時間・睡眠時間・睡眠の質・中途覚醒回数・気分（起床時）・気分（通所時））間のピアソン相関係数を、常に全期間のデータで算出して表示する（[stats.py](src/health_dashboard/stats.py) の `correlation_matrix`）。サイドバーの縦軸・期間の選択はこの表には影響しない。

- ｜r｜≥0.6を赤（相関が強い）、0.3〜0.6を黄（相関がありそう）で色分けする（[docs/07_correlation_table_image.jpg](docs/07_correlation_table_image.jpg) の手描きワイヤーフレームに基づく）。
- 対角線（同じ指標同士）とデータ不足で算出できないペアは「―」で表示する。
- 相関はあくまで数値上の関連であり因果関係を示すものではないため、表の直下に注意書きを表示している。

## 気象データ（気圧・天気）

気圧と天気を日報データの日付に結合し、縦軸（気圧（日平均）・気圧（前日差））、相関表、グラフのホバー表示（天気）、「天気ごとの平均」表として使える（[weather.py](src/health_dashboard/weather.py)）。

設定方法: リポジトリ直下の `weather_config.json` の `latitude`（緯度）・`longitude`（経度）に、施設の値を書き換える。`null` のまま、または値が不正な場合は気象データを使わず、通信も行わない（気象の軸は画面に表示されない）。書き換えた値は施設の位置情報になるため、GitHubなどに公開するリポジトリでは、書き換えたファイルをコミットしないよう注意する。

外部送信について: 他のデータと違い、この機能だけは実行時にインターネット通信を行う。送信先は気象API（Open-Meteo、APIキー不要）で、送る内容は「施設の緯度経度（小数点以下2桁）」「日付範囲」「取得項目」のみ。利用者名・日報・セルフケアの内容は一切含まない。取得結果は6時間キャッシュし、取得に失敗した場合は気象以外の機能をそのまま使える。

注意点:

- 取得値は気象庁の観測所の実測値ではなく、広域の再解析データ（格子単位）に基づく参考値である。
- 気圧は海面気圧の日平均、前日差は前日の日平均との差（hPa）。
- 天気は日降水量が1mm以上なら雨、降雪量が1cm以上なら雪、それ以外は平均雲量60%未満を晴・以上を曇として機械的に判定した目安で、実際の天気と食い違う日がありうる。判定基準は `weather.py` の定数で調整できる。
- 振り返りコメントは利用者の状態に対するものなので、気圧の軸ではコメントを出さず、相関表で関連を確認する形にしている。

## 出席状況

サイドバーの「表示」で「出席状況」を選ぶと、1週間（月〜金）を1つのデータとして、横軸を時間（週の開始日）にした次の2つのグラフを表示する（[attendance.py](src/health_dashboard/attendance.py)）。サイドバーの縦軸・期間の選択は影響せず、常に全期間を使う。体調マーカーは表示せず、相関表の対象にも含めない。

- 出席日数×出席率: 出席日数に出席率を掛けた値（満点は5）。欠席した週が、欠席の無い週より必ず低くなる。例: 4日出席・欠席なしは4.0、5日の予定で1日欠席（4日出席・80%）は3.2。
- 出席率の推移: 週ごとの出席率（%）。

出席日数は日報のある日、欠席日数は欠席フォームの提出日（日報のある日を除く）で、土日は数えない。出席率は「出席日数 ÷（出席日数 + 欠席日数）」で、日報も欠席連絡も無い日（休み・祝日など）は通所予定日に含めない。まだ終わっていない最新の週（金曜が今日以降の週）は、半端なデータのためグラフに含めない。

## 欠席した日の縦線

グラフ（「グラフ」表示）の、欠席した日の位置に縦線を引く。欠席フォームの「欠席理由」で色分けする。

- 赤: 精神的な理由（理由に「精神」を含む。例: 精神不調）
- 黄: 体調の理由（理由に「体調」を含む。例: 体調不良）
- 灰: それ以外（例: 通院）

同じ日に複数の欠席連絡がある場合は、精神的な理由＞体調の理由＞その他の順で1色にする。表示中の日付範囲にある欠席日だけを引き、日報のある日は引かない。利用者フォルダに「欠席」を含むExcelが無い場合は何も引かない。理由の分類は data_loader.py の classify_absence_reason で変更できる。

## 体調マーカーの区切り（個人ごとの自動割り振り）

体調ポイントを5段階（良好・普通・注意・警戒・異常）に分ける区切りは、その人の記録の分布から自動で決める（[condition_scheme.py](src/health_dashboard/condition_scheme.py)）。各マーカーの日数がなるべく揃うように、まず外れ値（Q3 + 1.5×IQR を超える点数。ただし5点未満は外れ値にしない）を「異常」とし、均等化の計算から除く。残りの日を、点数の低い順に良好・普通・注意・警戒の4区分へ、日数の目標との差の二乗和が最小になるよう分ける。同じ点数の日は同じ区分に入るため、0ptの日が多い人などでは完全には揃わない。点数の種類が4つ未満なら、良好から順に必要な数だけ使う。区切りの点数はグラフの下の凡例に表示する。

自動の区分は「その人の中での相対的な位置」で、点数が全体的に高い人でも良好と判定されうる。自動の区分で「良好」に3pt以上の日が含まれる場合は、グラフの下にその旨の注意書きを出す。体調の記録がある日が14日未満の場合は、自動では決められないため、目安の点数基準（0pt=良好、1〜2pt=普通、3pt=注意、4pt=警戒、5pt以上=異常）を使う。この区分は、グラフのマーカー、体調ストリークの検知、悪化ボーダー（体調が×になる割合）のすべてに反映される。点数の配置が異なる人（0ptがほとんど、全体に高い、二極、点数が1〜2種類のみ等）でも、エラーなく、点数が高いほど同じかより重い区分になることをテストで確認している（tests/test_condition_scheme.py）。

## 支援員向けの起動（ダブルクリック）

コマンドを使わずに起動するため、`体調分析を起動.bat`（Windows）と、その実体の `run_dashboard.py` / [launcher.py](src/health_dashboard/launcher.py) を用意している。

- ダブルクリックすると、画面（黒いウィンドウ）を出さずにダッシュボードを起動し、ブラウザで開く。すでに起動していれば、2つ目は起動せずブラウザだけ開く（既定のポートは8765）。
- 自分のPC内だけ（127.0.0.1）で待ち受け、利用状況の自動送信（テレメトリ）とエラーの詳細表示を止める。ツールバー（Deployボタン）も出さない。
- データ・設定の置き場所は、`%LOCALAPPDATA%\体調分析ダッシュボード`（`C:\Users\<ユーザー名>\AppData\Local\体調分析ダッシュボード`。`data/`、`weather_config.json`、`logs/`）。初回起動時に自動で作る。環境変数 `HEALTH_DASHBOARD_HOME` で別の場所にも変えられる。アプリ本体を入れ替えても、データと設定は消えない。ソースから `streamlit run app.py` で実行した場合は、従来どおりリポジトリ直下の `data/` を使う。
- この起動から開いたときだけ、サイドバーに「アプリを終了する」ボタンが出る。押すとサーバーが止まる。
- 起動に失敗したときは、メッセージ画面で知らせ、ログを `logs/launcher.log` に残す。
- `体調分析を起動.bat` は、同梱のPython（`python` フォルダ）があればそれを、無ければPCにインストールされたPython（`pythonw`）を使う。配布用のzip（Python同梱）の作り方は、次の「配布用zipの作成」を参照。

## 配布用zipの作成（Python同梱）

支援員のPCにPythonを入れなくても動かせるよう、Pythonとライブラリを同梱したzipを作る。Windowsで、次を実行する（[build_windows.ps1](packaging/build_windows.ps1)）。

```powershell
powershell -ExecutionPolicy Bypass -File packaging\build_windows.ps1
```

できあがる `dist/体調分析ダッシュボード-<バージョン>.zip` を、支援員のPCに渡す（`dist/` はgit管理の対象外）。zipを展開し、中の「体調分析を起動.bat」をダブルクリックすれば起動する。

- 同梱するもの: python.org の embeddable 版Python（既定は3.12.10）、`requirements-lock.txt` に固定したライブラリ、アプリ本体（app.py・src・起動用ファイル）、使い方（使い方.txt）。展開後は約500MB、zipは約160MB。
- 含めないもの: 利用者のデータ、`weather_config.json`、`.git`、テスト、docs。ビルドの途中で、xlsx・csv・weather_config.json・data・logsなどが混ざっていないことを確認し、混ざっていれば失敗にする。データと設定は、アプリの初回起動時に `%LOCALAPPDATA%\体調分析ダッシュボード` へ作られるため、アプリ本体を入れ替えても消えない。
- 同梱のPythonは、そのPCにインストールされたPythonやユーザー用ライブラリを使わない（`python312._pth` に `import site` を書かない）。PCごとに動きが変わる／同梱し忘れたライブラリがPC側のもので補われてしまうのを防ぐため。ビルドの最後に、検索パスがすべて同梱フォルダの中であることを確認する。
- ライブラリの版: `requirements-lock.txt` に、配布版のPythonで全テストが通った版を固定している。更新するときは、`requirements.txt` の指定で新しい版を取得して配布版のPythonで全テストを通してから、固定ファイルを差し替える（開発用の環境と配布版でpandasなどの版が違うことがあり、`None` と `NaN` の違いのように、版で動きが変わる箇所がある）。
- 動作確認: 展開したzipの同梱Pythonだけで全テスト（画面操作の通しテストを含む）が通ることと、PATHからPythonを外した状態でダブルクリック起動できること（約4秒）、終了ボタンで同梱Pythonのプロセスが全て終わることを確認した。何もインストールされていない別のPCや、ウイルス対策ソフトのある環境での確認は、まだ行っていない。
