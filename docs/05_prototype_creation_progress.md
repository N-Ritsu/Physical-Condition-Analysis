# プロトタイプ作成の進捗記録

- 作成日: 2026年9月15日
- 位置づけ: `01`〜`04`の設計文書をもとに実装したプロトタイプについて、開発当初の想定から変更・具体化された点を中心に記録する。設計文書自体の更新ではなく、実装時に判明した実データの制約や技術的制約への対応記録として扱う。

## 1. 概要

`03_requirements.md` の機能要件に沿って、Streamlit + Plotly + Pandas + ローカルLLM（Ollama）構成でダッシュボードのプロトタイプを実装した。実装にあたり、実際の日報データ・セルフケアシートの構造や、ローカルLLMの実機性能が当初の想定と異なっていたため、いくつかの点で設計を具体化・修正している。

## 2. データ構造に関する変更点

要件定義書は"日報CSVから日付・体調・睡眠時間・入眠時間・起床時間・中途覚醒回数・気分等を取得する"としていたが、実際のGoogleフォーム由来Excel（`日報データ.xlsx`）は列構成が異なり、以下の解釈・変換を実装した。

- 入眠時間は、独立した列がある想定だったが、実際には"就寝時間"列のみ存在した。さらに9〜11時台の値がAM/PMの区別なく記録されていた（例: 実際は21:30就寝でも`09:30`と記録）ため、6〜11時台の値はPM（+12時間）とみなす正規化処理を追加した（[data_loader.py](../src/health_dashboard/data_loader.py) `normalize_bedtime`）。
- 中途覚醒回数も、独立した列がある想定だったが、実際にはそのような列は存在せず、"睡眠の質"列の記述（例:「悪い, 中途覚醒３以上」）から正規表現で抽出する形にした。"中途覚醒３以上"は３回の中途覚醒として扱い、"早朝覚醒"の記載がある場合は中途覚醒回数+1として合算している。睡眠の質評価が複数併記されている行は、より悪い方（良好<普通<悪い）を採用する。
- 気分は、単一項目を想定していたが、実データは"気分（起床時）""気分（通所時）"の2系列だったため、両方を縦軸の選択肢として提供する形にした。
- 体調（マーカー表示）については、"セルフケアシート"（月別シート、睡眠・食事・ストレス・良好/注意/悪化サイン・回復対処のチェック表）から算出する体調ポイントに変更した。〇=0点・△=1点・✕=2点として全チェック項目を日ごとに合算し、0点=○良い／1〜4点=△普通／5点以上=×悪いの3段階に変換している（[data_loader.py](../src/health_dashboard/data_loader.py) `CONDITION_BAD_THRESHOLD`）。閾値5は実データの分布（0点を除く大半が1〜4点に集中し、7点以上は明確な外れ値）から暫定的に設定した値である。
- このほか、セルフケアシートの読み込み実装時に、月別シートの最初のデータ行（シート5行目）を読み飛ばすオフバイワンの不具合が実装中に見つかり、修正済み（回帰テストを追加）。

## 3. AI解説機能の設計変更（LLM単独 → ハイブリッド方式）

`03_requirements.md` は「Pandasで算出した統計サマリーをプロンプトに入力し、グラフ直下に150〜200文字程度の考察文を出力する」という、ローカルLLM単独での考察生成を想定していた。プロトタイプでも当初はこの方式（Ollama + qwen3:8b）のみを実装したが、実機（GPUなし・CPU実行）で検証した結果、1回の生成に数十秒〜数分かかることが判明した。支援員が毎朝複数の利用者・複数の軸を目視確認する運用（`01_interview_log.md`参照）には、この待ち時間は不向きと判断し、以下のハイブリッド方式に変更した。

- 既定表示は即時・LLM不使用とし、平均・直近値・期間前半後半のトレンドを条件分岐だけで文章化する（[rule_based_insight.py](../src/health_dashboard/rule_based_insight.py)）。待ち時間ゼロで、文面が事前に固定されているためガードレール（医学的判断をしない等）も構造的に保証される。
- これに加えて、任意でAIによる詳しい解説を呼び出せるようにした。折りたたみUI内のボタンから、これまで通りOllama（qwen3:8b）による自然な文章の解説を生成できる。面談前など時間に余裕がある場面向けの位置づけとした。

なお、qwen3系モデルは既定で"思考モード"が有効になっており、これがCPU実行時の遅延の主要因の一つだったため、LLM呼び出し時は`think=False`を指定して無効化し、詳しい解説側の生成時間もある程度短縮している。

両ロジックの統計計算部分（平均・直近値・トレンド算出）は[insight_context.py](../src/health_dashboard/insight_context.py)に共通化し、重複を避けている。

## 4. 技術スタックの実装状況

`03_requirements.md`記載のスタックは以下の通り導入済み。

- データ処理: Pandas 2.x, NumPy 2.x, openpyxl（要件定義書はCSV運用を想定していたが、実データがxlsxのため直接読み込みに対応。）
- UI・可視化: Streamlit, Plotly
- AI推論エンジン: Ollama + qwen3:8b（ローカル環境にインストール・動作確認済み）
- 品質管理: pytest（単体テスト40件、全通過）, ruff（lint、警告なし）

## 5. 開発環境に関する問題と対応

想定外の環境要因への対応も記録として残す。

- Windows/WSL混在によるPython環境の分離が問題になった。開発機はWindows PowerShellとWSL(Ubuntu)の両方から同じリポジトリを操作できる構成だが、Pythonの実行環境（pip install先）が別々になっており、一方にだけ依存パッケージを入れても他方では`ModuleNotFoundError`が発生した。両環境に`requirements.txt`をインストールすることで解消した。
- git push時にパスワードの再要求が続く問題も発生した。WSL側のGit Credential Manager（GCM）がGPG暗号化バックエンドを使用しており、GPGのpinentry（パスフレーズ入力）がTTYを正しく取得できずに復号失敗し、毎回PAT入力が必要になっていた。WSL環境にはOS標準のキーリング（GNOME Keyring等）がないため、`credential.credentialStore`を`plaintext`に切り替えて解消した。
- `.gitignore`のZone.Identifierパターンが一致しない問題もあった。WSLマウント越しにアクセスするWindowsのゾーン識別子ファイル（ダウンロード元マーク）のファイル名中の「:」が、通常のコロンではなく特殊なUnicode文字（U+F03A）としてエンコードされており、当初の`*.xlsx:Zone.Identifier`パターンが一致していなかった。`*Zone.Identifier`（コロン部分をワイルドカード化）に修正して解消した。

## 6. 現状の制約・今後の課題

- 体調ポイントの閾値が十分妥当でないため、細かな調整が必要。
- ローカルLLMを用いない、条件分岐での分析の精度が不十分。
- `03_requirements.md`にある"2変数間の相関係数の算出およびクロス集計テーブルの作成"は、計算関数（`stats.py`の`correlation`）のみ実装済みで、UI上での表示は未実装。
- ヒアリングで挙がっていた"季節性"を意識した長期（半年〜1年）比較のUIは未実装で、現状は直近1週間・直近1ヶ月・全期間の3種のみ。
- 複数利用者対応についても、現在は1人分のデータを前提とした構成であり、就労移行支援事業所での複数利用者運用を想定する場合、利用者切り替えUIなどが今後必要になる。
